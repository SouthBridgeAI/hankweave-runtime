## [0.12.0] - 2026-09-18

### Added

- **`hankweave pack` (U2 phase 2)** — packs a hank into a deterministic `.hank` bundle: a zstd-compressed PAX tar containing the hank's complete file closure plus a `hank.lock` (per-member sha256 + mode, per-codon input digests, `bundleHash`). Same source in, byte-identical archive out on one zstd build; `hank.lock` bytes, `bundleHash`, and the uncompressed tar bytes are identical across Bun and Node. Usage: `hankweave pack [hankPathOrDir] [-o out.hank] [--check] [--min-runtime <semver>]` — `--check` lints without writing anything; the default output is `<meta.name>-<meta.version>.hank` in the current directory; a lint always runs first and errors abort before any write. Output groups findings by category and location, then shows a tree of the published bundle with file sizes and executable markers, including when piped. Findings print to stdout; bundle details print to stderr. Color is detected per stream from terminal capability and disabled when redirected. Exit codes: 0 success, 1 lint/pack failure, 2 usage. A sidecar `hank.lock` (byte-identical to the embedded one) is written next to the source `hank.json` after the bundle commits. `tar -tf` reads a `.hank` unchanged. Requires Node ≥22.15 or Bun for zstd (a named error says so otherwise; `--check` works without it).
- `schemas/hank.lock.schema.json` — generated JSON schema for the machine-written lockfile.
- **`requirements.tools`** — hank authors declare the host programs a hank needs as bare names, e.g. `"requirements": { "env": ["DEEPSEEK_API_KEY"], "tools": ["bun", "jq"] }`. The runtime preflight resolves each name on PATH (Node and Bun alike; PATHEXT-aware on Windows) and fails fast with `Missing required tools on PATH: …` before any rig is built, mirroring the existing `requirements.env` check. Names are trimmed; empty names, whitespace, and path separators are rejected at schema time, and `hank.schema.json` documents the field for editors.
- `hankweave pack --no-lock` writes only the bundle, preserving source locks and supporting read-only hank directories. The embedded `hank.lock` is unchanged; help now recommends committing the default sidecar to track packed inputs.
- **Files the ignore rules drop from a `rigSetup` copy are now reported everywhere** — `--validate` and the startup summary warn per copy source (`Copy source "rig": 2 entries excluded by the default ignore rules: rig/app.log, rig/build`), the runtime emits the same line as an info event when the rig is planted, and `hankweave pack` keeps its `ignored-paths` warning; one shared formatter means the three cannot drift. Previously only `pack` said anything, and a prebuilt `dist/` or `*.log` fixture vanished from the workspace without a trace.
- **Run packed bundles directly:** `hankweave my.hank [data]` (also `.tar.zst`) and `--validate` verify every member's bytes and mode against `hank.lock`, recompute `bundleHash`, and enforce `runtime.min` before extraction. Extraction is content-addressed: every invocation of the same bundle lands at `<tmpdir>/hankweave-bundles/<bundleHash>`, reusing the tree when it still packs to the same `bundleHash` (the same closure walk `hankweave pack` runs), re-extracting it otherwise, and recreating it after temp cleanup — so the absolute prompt and rig paths an execution persists in its plan stay valid on resume. Replay uses the recorded extracted path. Verified configs stay byte-identical during run, validation, and replay. Integrity establishes self-consistency, not provenance. Requires Node ≥22.15 or Bun (zstd); Deno reports a clear unsupported-runtime error. Execution metadata is now version `1.2.0`, with `bundleHash` and absolute `bundlePath` for bundle runs only.

### Changed

- **BREAKING: gitignore handling is now git's own, everywhere** — two owners (`server/hank-dir.ts` for the hank source tree, `server/workspace/` for the agent workspace) answer every "which files are here, gitignore respected?" question by asking the real git binary, replacing two divergent hand-rolled interpreters (`copy-ignore.ts` for hank copy trees, `file-resolver.ts` for the agent workspace). Consequences:
  - **Hank copy trees (`rigSetup[].copy.from`), pack, and validation** are governed by ONE rules file — the hank root's `.gitignore` — which replaces the built-in defaults (`node_modules/`, `dist/`, `*.log`, …) when present, even if empty. Defaults apply only when the root file is absent. Scope rules into subfolders with path prefixes (`sub/build/`). A nested `.gitignore` inside a copied tree is now a validation error (`tree-nested-gitignore`, rejected like a symlink, with guidance to merge the rules into the root file); one elsewhere in the hank dir is inert. Verdicts are computed by real git against an immutable single-rules-file mirror in a temp dir (a mid-pack `.gitignore` edit cannot produce a tree judged under mixed rules; a parent repo's rules can never leak into a hank nested inside it), and the root rules file ships in the bundle so an extracted bundle repacks identically (`hank.lock` gains an advisory `ignoreDefaults` fingerprint so future runtimes can warn when built-in defaults drift). Hanks whose copy trees contain nested `.gitignore` files now fail validation instead.
  - **`.git` is always excluded, even when named explicitly** — a ref naming `.git` (directory, worktree/submodule marker file, or any path through one) is now a validation error (`git-metadata`), and `.git` entries inside copy trees are skipped regardless of authored negations.
  - **Workspace listings (checkpoints, file tree, watched files, archive)** run on `git ls-files` against the shadow checkpoint repo: ignored directories are never entered (no more full `node_modules` walks after an agent runs `npm install`), nested `.gitignore` semantics are exact, and rules are re-read live — a `.gitignore` the agent writes mid-run takes effect on the next listing (previously rules were frozen at first touch for the whole run). Contents of a git repo the agent clones into the workspace no longer appear in listings. Mandatory exclusions (`read_only_data_source/`, `rigArchive/`, hankweave state dirs) are enforced in-process and cannot be re-admitted by a workspace `.gitignore` negation; historical checkpoint entries under them are purged.
- **Watched-file matching uses live Git ignore rules** — `Write`/`Edit`/`MultiEdit` tracking now uses the workspace file domain in `server/workspace/`, replacing the cached ignore rules in `UnifiedFileResolver`. Tool-use events and checkpoints share the same fast-glob pattern dialect and live ignore verdict; mandatory exclusions now also cover `rigArchive/` and every `.git` path.
- **BREAKING (corner case)**: a bare data-directory positional literally named `pack` now selects the pack subcommand; write it as `./pack`.
- Pack closure hardening: bundle member names must be portable (no Windows-reserved device names, control characters, trailing dots/spaces, or case-fold collisions — files like `aux.txt` swept in by `copy.from` trees are refused with `non-portable-path`), and closures are bounded by deterministic quotas (1 GiB per member, 2 GiB total, 50k members — `closure-too-large`, refused before reading the oversized file). When `meta` is absent, `hank.lock`'s `name` falls back to `hank-<bundleHash prefix>` (derived from bundle bytes, not the source directory's basename), so identical bytes produce identical locks regardless of where the folder sits; the default bundle *filename* still uses the directory name.
- **`hankweave pack` no longer guesses host tools.** The `tool-dep` lint warning and the `requirements.tools` array in `hank.lock` are gone, along with the shell tokenizer that produced them: it split rig commands on `&&`/`;`/`|` without understanding quotes, redirections, or `$( … )`, so the lock shipped phantom names (`final`, `>`) and missed real dependencies (`jq` inside a substitution). Tool requirements are now what the author declares in `hank.json` (which ships inside the bundle) and are enforced by the runtime, not inferred by pack. The lock's `requirements` object is removed altogether — its `env` copy was redundant with the `hank.json` member, which is the single source of truth for both `env` and `tools`. `bundleHash` is unaffected (the object was never part of the identity payload) and `codonInputs` digests are unchanged too: `requirements.env` still feeds every codon's preimage, so an env-list edit still invalidates every codon.

### Fixed

- Pack default filenames now slug names with spaces or punctuation (for example, `docs-hank page` becomes `docs-hank-page-1.0.0.hank`) while retaining path safety checks. Stale publish-lock warnings now name the dead PID or identify unreadable contents.
- **Checkpoint staging is injection-safe** — files are staged with `--` and `:(literal)` pathspecs, so a file named `--all` or `:(glob)…` can no longer be misread as an option or pathspec magic.
- **Legacy stray `.gitignore` at the execution root is cleaned up** — an older initializer wrote a `rigArchive/` stanza to a location git never read; the stanza is now removed (user content in that file is preserved).
- **Directory names in `checkpointedFiles`/`archiveOnSuccess` now work** — a plain directory name like `"shim"` resolves to the directory's non-ignored contents, as the schema always promised (previously it silently matched nothing).
- **Checkpoints record deletions** — a tracked file the agent deletes is now staged as a removal in the next checkpoint (previously the deletion was never recorded and the file lived in every later snapshot).
- **Shutdown during loop finalization no longer drops remaining iterations** — the next loop iteration is saved to the execution plan even when shutdown interrupts codon finalization, so resuming continues the loop instead of silently skipping its remaining work.
- **Rollback removes new checkpoint-covered files absent from the target** — files created since the target checkpoint are removed even if they were never committed to a checkpoint, provided they belong to the abandoned execution's checkpoint selection. A recovery snapshot preserves their contents before removal; files outside that selection remain untouched.
- **Rig `copy.to` targets are checked consistently during validation and execution** — `--validate` now rejects absolute paths, paths escaping the workspace, and protected destinations such as `.hankweave/` or paths containing `.git`, using the same check as the runtime copy. Invalid targets fail early with the specific reason instead of passing validation and failing during rig setup.
